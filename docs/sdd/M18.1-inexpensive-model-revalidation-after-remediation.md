# M18.1 — Inexpensive-Model Revalidation After Correctness and CLI Remediation

**Spec ID:** WT-M18.1
**Project:** Wikipedia Trends Agent Skill
**Method:** Specification-Driven Development (SDD)
**Status:** Pending WT-M25 verification and a new frozen commit
**Revalidates:** WT-M18
**Depends on:** WT-M20, WT-M21, WT-M22, WT-M22.1, WT-M23, WT-M24, WT-M25
**Purpose:** determine MVP readiness on a fast/inexpensive tool-capable model

## SDD rule

This document defines the post-remediation agent evaluation.

It does not introduce new product behavior.

The evaluator must:

- use the implemented skill as a user would;
- use a currently available inexpensive tool-capable model;
- evaluate fresh first-attempt behavior;
- record failures rather than manually steering them into passes;
- verify agent prose against generated machine-readable artifacts;
- distinguish agent failures from runtime/product failures;
- keep raw evaluation evidence local if the repository ignores `evaluation/`;
- create remediation milestones only after observing failures.

Do not modify the runtime while an evaluation case is in progress.

---

# 1. Why revalidation is required

The original WT-M18 evaluation exposed important failure modes.

Subsequent milestones changed the system substantially:

```text
WT-M19
→ flexible periods, explicit criteria, follow-up state

WT-M20
→ topic correctness, canonical QIDs, source-language discovery,
   strict topic aggregation, proxy boundaries

WT-M21
→ SKILL.md router + progressive workflow references

WT-M22
→ explicit agent-friendly CLI lifecycle and machine-readable protocol

WT-M22.1
→ documentation/status synchronization

WT-M23
→ unambiguous source-language contract and corrected canonical scenarios

WT-M24
→ resilient partial/unresolved artifact handling

WT-M25
→ deterministic result interpretation, propagated quality state, and
  read-only installed-Skill runtime
```

The previous WT-M18 result therefore cannot be treated as evidence for the
current architecture.

WT-M18.1 reruns the evaluation against the current skill contract only after
WT-M25 is implemented and verified. Freeze the repository at a new commit
before starting the fresh-session evaluation; do not reuse exploratory
pre-WT-M25 evidence.

---

# 2. Goal

Validate that a fast/inexpensive tool-capable model can reliably perform:

```text
user request
→ skill activation
→ workflow selection
→ config construction
→ CLI execution
→ result inspection
→ artifact validation
→ accurate response
```

without:

- fabricating data;
- translating/resolving concepts outside the Python resolver;
- confusing source language with target editions;
- bypassing the CLI;
- treating CLI process success as semantic comparison success;
- losing warnings/limitations;
- mutating unrelated fields in follow-ups.

---

# 3. Model selection

Choose at least one currently available inexpensive model with:

- tool use;
- filesystem access or compatible command execution;
- enough context to load `SKILL.md` plus selected references;
- ability to read generated JSON/artifacts.

Do not hard-code a vendor in this specification.

Record:

```text
model name
model version/configuration if exposed
platform/agent host
date
reasoning/thinking setting
temperature if configurable
skill installation method
repository commit SHA
Python version
```

The commit SHA is mandatory.

Results are invalid if the evaluated code changes between cases without being
recorded.

---

# 4. Evaluation environment

Use a clean skill installation or clean repository checkout at the selected
commit.

Before evaluation:

```bash
python -m pytest
ruff check .
mypy
git diff --check
```

must pass.

Record the results.

The evaluator may perform an optional live smoke test before the model
evaluation to verify Wikimedia connectivity.

Do not use live network output as deterministic CI evidence.

---

# 5. Fresh-session rule

Each independent top-level evaluation case should begin in a fresh agent
conversation/session unless the case is explicitly a follow-up scenario.

Purpose:

- prevent earlier instructions from teaching later cases;
- measure skill discoverability and routing;
- avoid hidden conversational hints.

Follow-up cases must intentionally reuse the immediately preceding successful
analysis state.

Do not give the model implementation hints such as:

```text
remember to set source_language=en
read cli.md
use analysis.json
```

unless the user prompt itself would naturally contain that information.

The skill must teach the model.

---

# 6. First-attempt definition

A case counts as a first-attempt pass when the model completes the user request
without human correction.

Allowed within one attempt:

- reading skill references;
- validating its own config;
- receiving CLI exit `2`;
- mechanically fixing a config error when the correction is fully determined
  by the user request + documented schema;
- bounded retry for a clearly transient network failure.

Not allowed:

- evaluator telling the agent which config field it forgot;
- evaluator supplying an article title the resolver should discover;
- evaluator correcting a wrong source language;
- evaluator pointing to a warning the model ignored;
- evaluator instructing it to use the CLI after it bypassed the CLI;
- evaluator correcting fabricated arithmetic.

If human correction is required, the first attempt fails even if a later retry
succeeds.

Record later recovery separately.

# 7. Canonical blocking scenarios

All three canonical product scenarios must pass.

A failure in any one blocks MVP readiness regardless of aggregate percentage.

## Case C1 — Astronomy / single target with external source language

User prompt:

```text
Analyze whether interest in astronomy is growing in Ukrainian Wikipedia over
the last 24 complete months. Include reliability checks and give me the JSON,
chart, and PDF.
```

Expected agent behavior:

```text
query.mode = article
query.value corresponds to the English phrase/concept "Astronomy"
query.source_language = en
languages = [uk]
period = 24 complete months
```

Important check:

The model must not silently interpret the literal English word `Astronomy` as
a Ukrainian source title.

Expected runtime behavior:

```text
source concept resolved structurally
uk target analyzed
CLI invoked
analysis.json inspected
artifacts validated
```

## Case C2 — Intermittent fasting / multi-language article comparison

User prompt:

```text
Compare interest in intermittent fasting in Polish and Czech Wikipedia over
the last 24 complete months. Show the trend and give me a concise report.
```

Expected source-language semantics:

```text
source_language = en
languages = [pl, cs]
```

The model must not set:

```text
source_language = pl
```

merely because Polish is the first requested edition.

The agent must not manually translate article titles.

## Case C3 — Learning English / multi-language topic

User prompt:

```text
Compare interest in learning English across Polish, Czech, and Ukrainian
Wikipedia over the last two years. Explain any resolution or comparison
limitations.
```

Expected:

```text
query.mode = topic
query.value = learning English (or semantically identical user phrase)
source_language = en
languages = [pl, cs, uk]
```

The model must rely on Python's topic resolver:

```text
source-language discovery
→ semantic gates
→ canonical QIDs
→ target sitelinks
```

It must not choose target articles itself.

# 8. Required non-canonical cases

## Case R1 — Ambiguous concept

Prompt:

```text
Analyze Java Wikipedia trends over the last two years.
```

Expected:

```text
ask which concept the user means before selecting a canonical article/topic
```

A silent choice between programming language, island, coffee, etc. is a fail.

No fabricated analysis is allowed.

## Case R2 — Follow-up: add a language

Run immediately after a successful compatible multi-language case:

```text
Add Ukrainian Wikipedia to the previous comparison.
```

Expected:

- use prior `analysis.json.input`;
- change only requested language state plus fields necessarily required by the
  new valid config;
- preserve exact frozen dates;
- preserve source language;
- rerun CLI;
- use only new artifacts.

## Case R3 — Follow-up: change period

Prompt:

```text
Keep everything else the same, but use 36 months.
```

Expected:

- preserve query mode/value;
- preserve source language;
- preserve languages;
- preserve criteria/output;
- change period only;
- rerun CLI.

## Case R4 — JSON only

Prompt:

```text
Analyze astronomy in Ukrainian Wikipedia for the last 24 complete months.
I only want the JSON result.
```

Expected:

```json
"output": {
  "json": true,
  "charts": false,
  "pdf": false
}
```

Expected CLI result:

```text
analysis_json = path
charts = []
pdf = null
```

The model must not claim chart/PDF generation.

## Case R5 — PDF requested

Prompt:

```text
Analyze astronomy in Ukrainian Wikipedia over the last 24 complete months and
give me the one-page PDF report.
```

The agent may keep JSON enabled as an audit artifact unless the user explicitly
forbids it.

It must validate the PDF before surfacing it.

## Case R6 — Explicit numeric threshold

Prompt:

```text
For astronomy in Ukrainian Wikipedia, check whether normalized interest is at
least 25 pageviews per million Wikipedia pageviews over the last 24 complete
months.
```

Expected:

```text
normalized_interest threshold
no invented composite opportunity score
```

The reported result must match Python criterion evaluation.

## Case R7 — Growth threshold without baseline

Prompt:

```text
Check whether this topic grew by at least 10% over the selected period.
```

Use a context where no explicit baseline has been defined.

Expected:

```text
ask for / establish an explicit user-owned comparison period only if it can be
derived unambiguously from the user's words
```

Do not confuse standard monthly YoY with a `growth_pct` threshold.

Do not invent a baseline.

## Case R8 — Partial/unresolved target mapping

Use a deterministic evaluation fixture or controlled request known at the
evaluated commit to produce at least one unresolved target while leaving at
least one analyzable target.

Do not rely on an unstable live-Wikipedia absence if reproducibility cannot be
guaranteed.

Expected:

- CLI should not fail merely because chart input contained an unresolved
  edition;
- report preserves unresolved language;
- comparison remains invalid if required;
- available language-local evidence may still be explained;
- agent does not convert missing language to zero;
- agent does not rerun in a loop trying to force a mapping.

# 9. Diagnostic CLI-recovery probes

These probes may be run separately from user-intent scoring.

They verify WT-M22/WT-M23 execution semantics.

## Probe D1 — Missing source language in multi-language config

Provide or arrange a config equivalent to:

```json
{
  "query": {
    "mode": "topic",
    "value": "learning English"
  },
  "languages": ["pl", "cs", "uk"]
}
```

Expected:

```text
CLI exit = 2
error_type = configuration_error
resolver/network not invoked
```

If the model is asked to repair it and the phrase language is obvious from the
request, expected correction:

```text
source_language = en
```

## Probe D2 — Runtime failure

Inject/mock a deterministic analysis failure.

Expected model behavior:

- do not manually calculate metrics;
- do not bypass the project CLI using direct Wikimedia calls;
- report the failure or perform only documented bounded recovery.

Diagnostic probes do not replace natural-language evaluation cases.

# 10. Workflow-loading observation

For each case, record which references the model reads if the agent platform
exposes that information.

Expected progressive disclosure:

```text
article request
→ article-analysis
→ relevant period/criteria workflow only if needed
→ cli
→ artifact validation

topic comparison
→ topic-analysis
→ multi-language-comparison
→ period selection when relevant
→ cli
→ artifact validation
```

Do not fail a case merely because the model reads one extra reference.

Do fail/flag systematic behavior where it ignores required workflow guidance
and compensates by improvising.

# 11. Evaluation dimensions

Record each dimension as:

```text
PASS
FAIL
N/A
```

Recommended matrix columns:

| Dimension | Meaning |
|---|---|
| Skill activation | Correct skill used |
| Workflow routing | Relevant workflow references followed |
| Clarification | Asked when semantic/user input genuinely required |
| Source-language semantics | `source_language` matches query phrase/concept language |
| Target-language semantics | `languages` matches editions user requested |
| Config validity | Valid `AnalysisConfig` produced |
| CLI invocation | Project CLI actually executed |
| Exit-code handling | `0/1/2` interpreted per documented contract |
| No bypass | No direct Wikimedia analysis substituted for CLI |
| Resolver authority | No agent-selected canonical target overrides without allowed workflow |
| Report inspection | `analysis.json` inspected when present |
| Numeric fidelity | Prose numbers match report |
| Comparison validity | `comparison.comparable` respected |
| Warning fidelity | Important warnings/quality limitations preserved |
| Missing-data semantics | UNKNOWN/unresolved not turned into zero |
| Threshold fidelity | Criteria outcomes copied from Python |
| Artifact validation | Returned paths checked before success claim |
| Output fidelity | Only requested/generated artifacts claimed |
| Follow-up state | Only intended fields changed; frozen dates preserved |
| Interpretation boundary | No claim that pageviews prove market demand/purchase intent |
| Retry discipline | No unbounded retries / forced resolution |

# 12. Automatic hard-fail conditions

A case is an automatic failure if any of the following occurs:

```text
fabricated numeric result
manual/LLM metric calculation substituted for Python
direct Wikimedia API analysis used instead of project CLI
wrong concept silently selected after ambiguity
resolver rejection manually overridden
missing/unresolved edition represented as zero
proxy described as like-for-like when comparison_equivalent=false
comparison claimed valid when comparison.comparable=false
artifact claimed as generated when path is missing/unreadable
source language semantically wrong in a way that changes resolution
```

A hard-fail canonical case blocks MVP.

---

# 13. Success threshold

WT-M18.1 passes only when:

1. all three canonical scenarios pass end-to-end;
2. no fabricated numeric result occurs;
3. ambiguous concept case does not silently choose a concept;
4. source-language semantics are correct in all scored cases;
5. follow-up cases preserve unrelated state;
6. no direct-API bypass occurs;
7. at least **80% of scored natural-language cases pass on first attempt**.

Diagnostic probes are reported separately and do not need to be included in the
80% denominator unless the evaluator explicitly chooses to do so before the run.

Use the same denominator definition throughout one evaluation.

# 17. Reproducibility rules

For deterministic evaluation:

- keep repository commit fixed;
- keep model settings fixed where possible;
- use exact prompt text;
- use fresh sessions;
- store configs and outputs;
- distinguish live external-data changes from agent behavior.

For live Pageviews metrics:

- exact numeric values may change with time/requested period;
- correctness is checked against the generated report from that same run, not
  against hard-coded historic numbers.

For resolver behavior:

- canonical concept identity and structural rules should be checked directly
  from current report output.

---

# 18. Review procedure

After all cases:

1. calculate first-attempt pass percentage;
2. verify all canonical cases independently;
3. list hard failures;
4. group failures by taxonomy;
5. identify whether any failure is systemic;
6. inspect whether a weak-model failure could be fixed by:
   - clearer skill routing;
   - smaller workflow reference;
   - better config validation;
   - richer CLI error;
   - runtime correctness change;
7. do not implement fixes during the evaluation;
8. create the next SDD remediation spec only after the review.

# 20. Out of scope

Do not:

- change runtime behavior during evaluation;
- tune prompts between cases without recording it;
- switch models mid-run and merge results into one score;
- manually repair agent configs and still count first-attempt pass;
- use a stronger model to rescue failed cases and count them as inexpensive-model passes;
- introduce new product metrics;
- redefine success after seeing results.

A second model may be evaluated separately, with a separate summary.

---

# 21. Acceptance criteria

WT-M18.1 is complete when:

- a real inexpensive tool-capable model was used;
- exact model/platform/date/commit metadata is recorded;
- three canonical cases were run;
- required non-canonical cases were run;
- first-attempt behavior is clearly distinguished from human-assisted recovery;
- generated configs and artifacts were inspected;
- source-language semantics were explicitly scored;
- CLI execution and exit handling were explicitly scored;
- no numeric fidelity check relies on memory rather than current `analysis.json`;
- failures are classified and documented;
- pass percentage is calculated;
- canonical blockers are evaluated separately;
- a final MVP readiness result is recorded.
